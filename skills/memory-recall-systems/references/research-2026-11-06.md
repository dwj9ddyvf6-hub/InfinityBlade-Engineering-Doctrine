# LLM Agent Memory, Recall, Context and Long-Running Execution — State of the Art (2025–2026)

**Prepared:** 2026-11-07 (all web sources read via search index / page fetch on 2026-11-07; no live-browser interactive verification was performed — figures are flagged *index* throughout).
**Audience:** Two collaborating AI agents (personal-assistant + coding/trading) on one small Linux VM, currently using file-based memory: markdown memory files, summaries injected at session start, searchable archives, plus scheduled background jobs. Known pain points: compaction loses early detail; retrieval depends on remembering to search; long jobs have been OOM-killed.

## Interpretation update (3.2.0)

This report is a dated research record, preserved with its original figures and source limits. It is not a fresh verification of every linked source. Compare only matching benchmark versions, splits, answer models, judges and metrics. A reported 6.4% flawed answer-key rate does **not** mathematically establish a universal 93.6% achievable-score ceiling: it depends on the audited sample, scoring and whether a system reproduces the erroneous key. Likewise, “no independently-run comparison exists” below describes this search's coverage, not a proof of worldwide absence. Star counts, prices, licenses and release behavior require a current source read before adoption. Local adoption evidence is the adopter's canary/task outcomes; the external figures motivate tests rather than prove results here.

## Read this first: the benchmark warning

Almost every headline accuracy number in this field is **vendor self-reported and not comparable across systems**. The same system scores tens of points apart depending on the answer model, judge model, judge prompt, harness, and benchmark variant. The clearest documented example: Zep's LoCoMo score has been reported as **75.14% ±0.17 (Zep-corrected), 65.99% (Mem0 paper), and 58.44% (a Mem0 re-run)** — via https://arize.com/blog/alyx-agent-long-term-memory-architecture/. An independent audit of LoCoMo itself found **99 of 1,540 reference answers (6.4%) factually wrong**, putting the effective ceiling near 93.6%, and another analysis found the judge accepts **62.81% of deliberately wrong answers**. Any score at or above ~93.6% on LoCoMo should be treated as suspect. Throughout this report, prefer: papers > primary docs/repos > independent audits > vendor blogs > secondary roundups. Numbers below are given with their provenance so the reader can discount accordingly.

A second framing result matters for a file-based setup: in the Mem0 paper's own evaluation, **full-context prompting (72.90% J on LoCoMo) beat every memory system on raw accuracy** — memory systems won on cost and latency (Mem0 used >90% fewer tokens and ~91% lower p95 latency). And Letta reported that a plain GPT-4o-mini agent storing history in **files with grep-style search scored 74.0% on LoCoMo**, ahead of most structured memory systems on that harness. Structure is not automatically better than well-organised files; it is better at scale, cost and latency.

## Summary

- The field converged in 2025–26 on a layered model — **working / episodic / semantic / procedural** memory — and on a Dec 2025 survey taxonomy of **Forms (token-level / parametric / latent) × Functions (factual / experiential / working) × Dynamics (formation / evolution / retrieval)** (Hu et al., "Memory in the Age of AI Agents", arXiv:2512.13564, https://arxiv.org/abs/2512.13564).
- The strongest *practical* evidence for a small file-based setup is not a memory database at all: it is (1) **observation masking / tool-result clearing** (JetBrains: matched or beat LLM summarisation while cutting cost >50%), (2) **externalised structured state** (progress files, feature lists, todo recitation — Anthropic + Manus), and (3) **hybrid BM25+vector+rerank search over the existing markdown with a harness rule that forces searching** (QMD pattern; BM25 alone hit 96.2% any-hit@5 on LongMemEval-S in agentmemory's component test).
- Newer benchmark generations (BEAM, LongMemEval-V2, MemoryArena, MemoryAgentBench) show the frontier problem has moved: **recall at 1M–10M-token scale, using memory to act, and conflict resolution / selective forgetting (best score only 28%)** are all still weak. In LongMemEval-V2, a **file-store + coding-agent evidence-gathering approach scored 72.5%, beating plain RAG (48.5%)** — encouraging for this exact setup.
- For two agents, the research consensus is a **governed shared store** (blackboard pattern): shared memory must be persistent, queryable, and scoped/enforceable; a plain shared vector store fails the third requirement.

## 1. Long-term memory architectures

### Taxonomy

**Memory in the Age of AI Agents (survey, Dec 2025, 47 authors)** — Replaces the crude long/short-term split with Forms × Functions × Dynamics, where "evolution" explicitly includes consolidation, updating and forgetting as first-class operations. This is the best current map of the design space. Source: https://arxiv.org/abs/2512.13564 (discussed at https://github.com/lin-guanguo/llm-memory-research/blob/HEAD/memory-survey-2026.research.md).

**Practitioner convergence** — Working + episodic + semantic + procedural layers; LangChain frames the corresponding *context engineering* operations as **Write / Select / Compress / Isolate**. Procedural memory (the agent rewriting its own instructions/playbooks) is the newest widely-adopted layer and the one with the highest governance risk (see §7).

### The named frameworks

**Letta (formerly MemGPT)** — https://github.com/letta-ai/letta — 25,370 stars, Apache-2.0 (read 2026-11-07). OS/virtual-memory model from the MemGPT paper (arXiv:2310.08560): the agent self-edits **core memory blocks** (always in context — persona, human, custom), pages to/from **recall** memory (full searchable conversation history, hybrid search) and **archival** memory (long-term semantic store). Two 2025–26 developments matter most: **MemFS**, a git-backed markdown memory filesystem with YAML frontmatter where `system/` files are always loaded and the rest lazily — i.e. Letta itself converged toward the file-based approach this audience already uses; and **sleep-time / dreaming agents**: background subagents that consolidate and rewrite memory blocks off the interactive path, triggered by step count or compaction. The underlying Sleep-time Compute paper (arXiv:2504.13171, Apr 2025) reports ~5× less test-time compute for equal accuracy and 2.5× lower cost per query amortised. Note: the repo README now points to `letta-ai/letta-code` as the current source; the V1 API is a legacy/archive branch.

**Mem0** — https://github.com/mem0ai/mem0 — 68,531 stars, Apache-2.0 (read 2026-11-07). An extraction pipeline rather than a store: an LLM extracts candidate salient facts from each new message pair (conditioned on a running summary + last 10 messages), then an update phase compares each candidate against the 10 most similar stored memories and tool-calls **ADD / UPDATE / DELETE / NOOP**. Paper (arXiv:2504.19413, ECAI 2025): LoCoMo J-scores **Mem0 66.88%, graph variant Mem0^g 68.44%, best RAG 60.97%, full-context 72.90%**; Mem0 p95 latency 1.44s vs 17.12s full-context; ~1,764 vs ~26,031 tokens per query. The graph variant won temporal questions (58.13) but lost single/multi-hop and cost ~3× latency, ~2× tokens. **Important 2026 change** (repo README): the algorithm moved to single-pass **ADD-only** extraction (no UPDATE/DELETE), entity linking, and multi-signal retrieval (semantic + BM25 + entity, fused); the graph module was removed from OSS v3 and remains only on the hosted Platform. The new headline numbers (LoCoMo 92.5, LongMemEval 94.4, BEAM 64.1 @1M) are **platform-only, not the open-source SDK** — do not expect them from a self-hosted install.

**Zep / Graphiti** — https://github.com/getzep/graphiti — 32,605 stars, Apache-2.0, created 2024-08-08 (read 2026-11-07). A **temporal knowledge graph**: raw episodes (with provenance) feed a semantic entity/edge subgraph and a community subgraph. Edges are **bi-temporal** — `valid_at/invalid_at` (when the fact was true in the world) plus `created_at/expired_at` (when the system learned it) — and contradicted facts are **invalidated, not deleted**, preserving history. Retrieval fuses cosine + BM25 + graph BFS (RRF/MMR) with **no LLM in the search path**, which keeps latency low. Paper (arXiv:2501.13956, Jan 2025): DMR **94.8% vs MemGPT 93.4%**; LongMemEval-S **71.2% (gpt-4o) vs 60.2% full-context**, latency 28.9s→2.58s, context 115K→1.6K tokens; one category (single-session-assistant) regressed −17.7%. Caveats: Zep's hosted Community Edition was retired in 2025; Graphiti requires running your own graph DB (Neo4j/FalkorDB/Neptune; Kuzu support deprecated) — real weight on a small VM.

**Cognee** — https://github.com/topoteretes/cognee — 33,114 stars, Apache-2.0 (read 2026-11-07). An Extract-Cognify-Load pipeline: chunk → extract (subject, relation, object) triples → summarise → embed and commit to a graph (default embedded Ladybug/Kuzu + LanceDB; Postgres/Neo4j/pgvector profiles available). Since 1.0 the API is `remember / recall / improve / forget`, and it can now run locally with small models/GLiNER with no LLM key needed for basic remember/recall. Its paper (arXiv:2505.24478) is about the KG↔LLM interface on HotPotQA/2Wiki/MuSiQue and is first-party/preliminary; **no independent LoCoMo/LongMemEval score is published in the repo** — the weakest evidence-to-stars ratio among the big repos.

**LangMem / LangGraph** — https://github.com/langchain-ai/langmem — 1,750 stars, MIT, created 2025-01-21 (read 2026-11-07). Primitives rather than a product: namespaced JSON documents (user/session/agent scopes) over LangGraph's `BaseStore` with a vector index; **hot-path** memory tools the agent calls mid-conversation plus a **background manager** that extracts/consolidates asynchronously; semantic, episodic and **procedural** memory (it can rewrite the agent's own system prompt). No published LoCoMo/LongMemEval score. Flag: low release activity (0 GitHub releases; PyPI last release Oct 2025 per a secondary check on 2026-11-04) — treat as a patterns library, and note LangGraph's checkpointing (§4) is the more valuable part for this audience.

### Newer 2025–2026 entrants

**Hindsight (Vectorize)** — https://github.com/vectorize-io/hindsight — 59,435 stars, MIT, created 2025-10-30, 75 releases (read 2026-11-07). Retain/Recall/Reflect over **typed memory networks** that separate world facts, the agent's own experience, observations/summaries, and evolving beliefs/mental models; a background Reflector consolidates. Retrieval runs semantic + BM25 + graph + temporal in parallel. Paper (arXiv:2512.12818, Dec 2025) reports LongMemEval improving 39.0%→83.6% with an open 20B backbone; vendor/leaderboard claims reach **91.4% LongMemEval, 89.61% LoCoMo**, with independent reproduction by Virginia Tech + Washington Post collaborators claimed in the repo README. The paper itself warns that ~90% scores mean the classic benchmarks are saturating.

**Mastra Observational Memory (OM)** — Compression instead of retrieval: an **Observer** agent compresses raw messages at ~30K tokens into dense, dated, priority-tagged observations (3–6× compression on text, 5–40× on tool-heavy traffic); a **Reflector** condenses the observation log at ~40K tokens. The log stays in context as a **stable, cacheable prefix**. Mastra research (Feb 2026) claims **LongMemEval 94.87% with gpt-5-mini, 84.23% with gpt-4o** (vs 82.4% oracle) at ~30K average context. Sources: https://github.com/chocksy/cems/blob/HEAD/research/mastra-observational-memory.md and https://github.com/lin-guanguo/llm-memory-research/blob/HEAD/mastra.research.md. Vendor research, but the *pattern* (dated observation log as stable prefix) is cheap to copy in plain files.

**A-MEM** (NeurIPS 2025, arXiv:2502.12110) — Zettelkasten-style atomic notes (context description + keywords + tags + timestamp). On insert, a new note links to related notes and can trigger **memory evolution**: rewriting the descriptions/tags of linked older notes, so the store reorganises itself. ~60% LoCoMo per secondary comparison matrices.

**MIRIX** (arXiv:2507.07957, Jul 2025) — Six typed stores (Core, Episodic, Semantic, Procedural, Resource, Knowledge Vault), each run by a manager agent under a Meta Manager. Paper claims +35% over RAG on ScreenshotVQA with 99.9% storage reduction (first-party, via secondary notes).

**MemoryOS (BAI-LAB)** (EMNLP 2025 Oral, arXiv:2506.06326) — OS-style short/mid/long-term hierarchy where promotion and eviction are governed by a **heat score** = α·visits + β·length + γ·exp(−Δt/μ). Reports +49.11% F1 / +46.18% BLEU-1 vs baseline on LoCoMo (absolute cross-system scores not reported). Not to be confused with MemOS below.

**MemOS (MemTensor)** — https://github.com/MemTensor/MemOS — ~12.3K stars, Apache-2.0, release v2.0.21 on 2026-10-29 (checked 2026-11-05 via https://agentgid.com/agents/memos/). A "memory OS" whose MemCube unifies plaintext, activation (KV-cache) and parametric memory with provenance, versioning and lifecycle management.

**FadeMem** (Jan 2026, arXiv:2601.18642) — Biologically inspired **differential forgetting**: Ebbinghaus-style decay with dual layers and promote/demote hysteresis (θ=0.7/0.3). Reports **45% storage reduction at comparable LoCoMo F1** and 82.1% critical-fact retention vs 78.4% for append-only (via https://github.com/wuesteon/lean-memory/blob/HEAD/docs/superpowers/specs/2026-07-16-sleep-time-maintenance-design.md). The older MemoryBank (2023) precedent — retention R = e^(−t/S), with S growing on each recall — captures the practitioner rule: **rank by decay, don't delete**.

**Supermemory** — https://github.com/supermemoryai/supermemory — 31,555 stars, MIT monorepo, created 2024-02-27 (read 2026-11-07). Hosted-first memory/context engine: fact extraction, static+dynamic user profiles, hybrid RAG+memory search, connectors, temporal/contradiction handling and forgetting. Caveat from secondary surveys: the self-host engine ships **binary-only** despite "open source" framing.

**Honcho (Plastic Labs)** — https://github.com/plastic-labs/honcho — 7,986 stars, AGPL-3.0 (read 2026-11-07). Reasoning-first, **peer-centric** user modelling: a background Deriver/Dreamer builds a representation of each peer (user or agent), queried via a dialectic chat interface. Vendor evals (https://honcho.dev/evals/, Dec 2025): **LongMemEval-S 90.4%, LoCoMo 89.9%, BEAM 0.630 @100K / 0.618 @1M / 0.409 @10M**, using only 11.4% of full context. Its peer model maps unusually well onto a two-agent + one-user setup.

**EverOS (EverMind-AI, formerly EverMemOS)** — https://github.com/EverMind-AI/EverOS — 13,842 stars, Apache-2.0, created 2025-10-28 (read 2026-11-07). Local-first and **Markdown-native**: conversations, files and trajectories are stored as readable Markdown (the source of truth) with derived SQLite + LanceDB indexes; user episodes/profiles are kept separate from agent cases/skills; offline "reflection" merges episode clusters and refines profiles/skills between sessions. Closest in spirit to this audience's existing setup. A self-published LoCoMo 93.05% (Feb 2026) lacks detailed methodology — flag per the benchmark warning.

**OpenViking (Volcengine)** — https://github.com/volcengine/OpenViking — 41,705 stars, **AGPL-3.0**, created 2026-01-05 (read 2026-11-07). A "context database": memories, resources and skills in one virtual filesystem under `viking://`, browsed with ls/tree/grep, with **progressive L0 (one-sentence abstract) / L1 (overview) / L2 (full content)** loading — every directory carries generated `.abstract.md` / `.overview.md` files. Vendor benchmark: LoCoMo 80–83% across three agent integrations (up from 24–57% native memory), input tokens down 34.3–91.0%.

**TencentDB Agent Memory (Tencent)** — Team-level memory hub reached via proxy fan-in; distils Chat Memory / Skill / LLM-Wiki / Code-Graph with L0–L3 progressive disclosure; grew 0→~17K stars in four months (~27–30.6K by Sept–Nov 2026). License is ambiguous (NOASSERTION detected; Tencent wrapper over an MIT badge) — **read the license before adopting**. Via https://github.com/evanmaranzano/ai-memory/blob/HEAD/docs/research-2026-landscape.md.

Also noted: **MAGMA** (arXiv:2601.03236, multi-graph memory, LoCoMo judge score 0.70, early 2026), SimpleMem, TiMem, MemRL, and Google's hosted Vertex AI Memory Bank (public preview Jul 2025, not open source).

### What the benchmarks say (see also §7)

- **LoCoMo** (ACL 2024, arXiv:2402.17753): 50 long conversations, single/multi-hop, temporal, open-domain and adversarial questions. The field's default, and now demonstrably noisy (see warning above).
- **LongMemEval** (ICLR 2025, arXiv:2410.10813; https://github.com/xiaowu0162/LongMemEval): 500 questions across information extraction, multi-session reasoning, temporal reasoning, knowledge updates and abstention; S ≈115K tokens, M up to 1.5M tokens. Headline finding: systems drop ~30–60% vs oracle conditions.
- **BEAM** (arXiv:2510.27246): histories up to **10M tokens**; even 1M-window models struggle.
- **LongMemEval-V2** (May 2026, arXiv:2605.12493): agent-trajectory memory up to 115M tokens. **Plain RAG 48.5%, authors' tuned RAG 57.8%, file-store + coding-agent evidence gathering 72.5%**, off-the-shelf coding agent 69.3% — the single most encouraging result for a file-based setup. Via https://github.com/zytech97/awesome-agent-memory-bench/blob/HEAD/README.md.
- **MemoryArena** (2026): memory must guide *action* across interdependent sessions; all methods score low (0.09–0.20 success) and **RAG baselines are at least as good as dedicated memory systems** — recall ≠ use.
- **MemoryAgentBench** (ICLR 2026): on **conflict resolution / selective forgetting, the best systems score ≤28%**, RAG/memory agents ≤7%. Forgetting well is the least-solved problem in the field.

**Bottom line for §1:** no architecture has a trustworthy, independently-replicated accuracy lead. The differentiators that survive scrutiny are: temporal validity handling (Graphiti), verbatim storage + good retrieval (MemPalace/files), background consolidation (Letta sleep-time, Hindsight Reflector, Mastra Observer), and cost/latency. Full context still wins on accuracy at LoCoMo scale; memory wins on economics.

## 2. Context management

**Anthropic, "Effective context engineering for AI agents" (29 Sep 2025)** — https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents (primary, read 2026-11-07). Defines context engineering as curating the smallest high-signal token set; context is a finite resource with an **attention budget** (attention cost grows ~n²). Techniques: **compaction** (summarise near the limit, reinitialise with the summary; Claude Code keeps critical details and discards redundant tool outputs), **structured note-taking** (NOTES.md / todo files persisted outside the window and read back), **sub-agent architectures** (clean windows returning condensed summaries), and **just-in-time retrieval** (keep lightweight identifiers — file paths, queries, links — and load at runtime; Claude Code uses glob/grep and `head`/`tail` on large data instead of loading files whole; upfront-loaded CLAUDE.md is the hybrid). Companion launch data: **context editing** (clearing stale tool results past a threshold) **+ memory tool** (a client-side `/memories` directory with a check-memory-first protocol) gave **+39% on internal agentic search (+29% from editing alone) and −84% tokens over a 100-turn web search**. A 2026 server-side compaction API (`compact_20260112`) triggers at 150K tokens by default; in Anthropic's research agent, compaction cut peak context 335K→169K tokens.

**Context rot — Chroma research (Hong, Troynikov, Huber, 14 Jul 2025)** — 18 frontier models degrade **non-uniformly at every length increment, well before the window is full, even on trivial tasks**; a single distractor hurts and four compound; low needle–question similarity degrades faster; a *shuffled* haystack beats a coherent one; on LongMemEval, focused ~300-token prompts beat full ~113K-token prompts consistently. Via https://glasp.co/articles/context-rot-rag-long-context-hybrid. Practical consequence: "it fits" is not "it works" — retrieval into a *small* context beats a big stuffed context.

**Lost in the middle** (Liu et al., TACL 2024) — U-shaped attention: best at the start and end of context, **>30% degradation in the middle** on multi-document QA. Mitigations: put critical state at the end (recitation, below), rerank-and-reorder retrieved evidence, keep contexts short.

**Context Length Alone Hurts Despite Perfect Retrieval** (arXiv:2510.05381, Oct 2025) — 13.9–85% degradation with length *even with perfect retrieval*; masking irrelevant text does not rescue performance; summarising retrieved evidence first helps slightly (~+4%). Argues for compressing evidence, not just selecting it.

**Manus, "Context Engineering for AI Agents" (18 Jul 2025)** — https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus?s=08&utm_source=www.theaivalley.com&utm_medium=referral&utm_campaign=chatgpt-agent-enters-the-action-era (primary). Production lessons: **KV-cache hit rate is the single most important metric** (input:output ≈100:1; cached input $0.30/M vs $3.00/M uncached on Claude Sonnet at the time); keep the prefix stable (no timestamps in the prefix), append-only history, deterministic serialisation, mask tool logits instead of removing tools (removal invalidates cache); **filesystem as context with restorable compression** (drop content, keep the URL/path so it can be re-fetched); **recitation** — rewrite `todo.md` every step (~50 tool calls/task average) to push the goal into recent attention, directly fighting lost-in-the-middle and goal drift; keep errors in context as evidence rather than hiding them.

**Observation masking beats summarisation — JetBrains Research, "The Complexity Trap" (1 Dec 2025, arXiv:2508.21433)** — https://blog.jetbrains.com/research/2025/12/efficient-context-management/. On SWE-bench Verified (500 instances, SWE-agent + OpenHands, up to 250 turns): **observation masking** (hide old tool/environment outputs, keep reasoning + actions, window = last 10 turns) vs **LLM summarisation** (summarise 21 turns, keep last 10 full). Both cut cost >50% vs unmanaged; **masking matched or beat summarisation in 4/5 settings** (Qwen3-Coder 480B: −52% cost, +2.6% solve rate). Summarisation produced **13–15% longer trajectories** (summaries obscure stopping signals) and >7% of total cost was the summariser calls themselves. Context: ~84% of tokens in a typical agent trajectory are observation/tool-output tokens, which is why masking has such leverage. Hybrid masking+summarisation was best in some configurations. Practitioner rule derived across sources: **clear/mask first (free, deterministic, reversible), summarise only genuinely complex history, and trigger proactively at ~60–75% context utilisation** rather than at the limit.

**ACE — Agentic Context Engineering** (arXiv:2510.04618, ICLR 2026; open source, Apache-2.0, github.com/ace-agent/ace) — Treats context as a structured **playbook** of ID'd bullets with helpful/harmful counters, edited by a Generator→Reflector→Curator loop via **delta ADD/UPDATE/REMOVE edits — never a monolithic rewrite**. It names the two failure modes that kill naive compaction: **brevity bias** (summarisers/optimisers drop domain detail for short generic text) and **context collapse** (one rewrite shrank a playbook 18,282 tokens / 66.7% accuracy → 122 tokens / 57.1%, *below* the 63.7% no-context baseline). Results: +10.6% AppWorld, +8.6% finance, −86.9% adaptation latency vs GEPA-style baselines. Direct lesson for summary files: **edit summaries incrementally; never regenerate them wholesale from the previous summary.**

**Summary drift** — Repeated summarisation-of-summaries compounds loss (see ACE's collapse, and SSGM's consolidation-stage drift in §7). Mitigations with support: keep raw episodes/files as ground truth and summarise *from raw*, not from summaries (restorable compression); hierarchical day→week→month digests (TiMem-style); dated observation logs instead of free prose (Mastra OM); a structured state object kept separate from any narrative summary.

**LLMLingua family (Microsoft)** — https://github.com/microsoft/LLMLingua — 6,806 stars, MIT (read 2026-11-07). LLMLingua (EMNLP 2023, arXiv:2310.05736) prunes tokens by small-model perplexity: **up to 20× compression at ~1.5% loss**. LongLLMLingua (ACL 2024) adds +21.4% on NaturalQuestions with ¼ the tokens and explicitly targets lost-in-the-middle. LLMLingua-2 (ACL 2024 Findings, arXiv:2403.12968) distils GPT-4 into a BERT token classifier: 2–5× compression, 3–6× faster than v1. Caveat for this audience: it needs a ~560M–7B compressor model resident — only the LLMLingua-2 class is plausible on a small VM, and masking/retrieval usually buys more first.

**KV-cache compression** (mainly for self-hosters; API users get caching, not compression) — PagedAttention/vLLM gives 2–4× throughput; quantisation (ZipCache 4.98× at 0.38% drop; KVTC up to 20×, Nov 2025) and eviction (Compactor, 20–68% memory cut, Jul 2025) go further. **Pitfalls of KV Cache Compression** (arXiv:2510.00231, Oct 2025) documents degradation on multi-instruction tasks and even system-prompt leakage — gate any eviction scheme behind needle evals and exhaust lossless levers (caching, paging, quantisation) first.

## 3. Recall and retrieval

**Hybrid lexical+vector+rerank is the measured winner.** A Redis-cited benchmark (23,088 queries over 7,318 financial documents, https://redis.io/blog/quality-context-ai-agents/): BM25 alone Recall@5 **0.644** beat dense-only 0.587; **hybrid + rerank reached 0.816 (+39% over dense)**; MRR@3 rose 0.433 (hybrid RRF) → 0.605 (with reranking). Lexical search is not a fallback — for names, tickers, IDs and exact phrases it is often the stronger channel.

**BM25 alone is surprisingly strong for agent memory.** agentmemory's component test (repo README, measured 2026-10-28, LongMemEval-S, 470 answerable questions): keyless **BM25 any-hit@5 96.2%, strict recall-all@5 84.7%**, vs a lexical baseline of 88.7%/72.1%. Repo: https://github.com/rohitg00/agentmemory.

**The MemPalace audit lesson.** MemPalace's headline 96.6% R@5 on LongMemEval was reproduced in an independent analysis (GitHub issue #29; arXiv:2604.21284) using **plain ChromaDB with the default all-MiniLM-L6-v2 embedder and the "palace" structure inactive** — i.e. at this scale, **verbatim storage + a decent embedder does most of the work**, and elaborate structure should have to prove its marginal value. (MemPalace's current README claims 98.4% R@5 for its held-out hybrid mode; repo read 2026-11-07: https://github.com/MemPalace/mempalace.)

**QMD — the best worked example for this exact setup** — https://github.com/tobi/qmd — 30,931 stars, MIT, created 2025-12-08 (read 2026-11-07). One SQLite file (FTS5 + sqlite-vec), **all-local models** (~2.2GB total: EmbeddingGemma-300M, Qwen3-Reranker-0.6B, and a 1.7B query-expansion model fine-tuned to emit typed `lex`/`vec`/`hyde` subqueries). Pipeline: BM25 + vector in parallel → **Reciprocal Rank Fusion (k=60)** → rerank top ~30 with position-aware blending that protects strong BM25 hits; expensive steps are skipped when the BM25 winner is clear (≥0.85, ≥0.15 ahead). `search` ~0.2s; full `query` ~2–3s warm. Field guide: https://vanja.io/how-qmd-works/. Its key harness lesson: **a search tool alone changes nothing — behaviour changes when a session-start instruction/skill forces search-before-answer.**

**Graph retrieval.** Graphiti (§1) fuses graph BFS with BM25/cosine and no LLM in the loop. **HippoRAG 2** (ICML 2025, arXiv:2502.14802): offline OpenIE triples form a KG used as a hippocampal index; query entities link in, and **Personalized PageRank** spreads activation for single-step multi-hop retrieval — average QA F1 59.8 vs NV-Embed-v2 57.0, GraphRAG 49.6, RAPTOR 48.8; Recall@5 +5.0% (MuSiQue) / +13.9% (2Wiki) over dense. High offline indexing cost; poor fit for rapidly mutating conversational state, good fit for stable knowledge (codebases, documentation, instrument references).

**Deciding what to write (salience & extraction).** Patterns in production systems: Mem0's 2025 extract-then-reconcile (ADD/UPDATE/DELETE/NOOP) vs its 2026 ADD-only turn — reconciliation proved error-prone and accumulation + retrieval-time reasoning tested better; Generative Agents' classic score = recency + LLM-rated importance (1–10) + relevance; Hindsight/Honcho/LangMem all extract **in the background, off the hot path**, with LangMem additionally offering hot-path tools when the agent itself should decide. Converged pattern: **capture cheaply and verbatim inline; consolidate asynchronously** (sleep-time, §1/§4).

**Progressive disclosure** (used by claude-mem, agentmemory, TencentDB, OpenViking): search returns a compact index (~50–100 tokens/result) → a timeline view (~200 tokens) → full records (~500–1,000 tokens) only for chosen IDs — roughly a **10× token saving** vs dumping full results into context, and it composes with §2's rot findings.

**Memory linking/association.** A-MEM's evolving Zettelkasten links, Graphiti's entity graph, and Hindsight's typed networks are three points on one spectrum: links let retrieval return *associated* context (the meeting where a decision was made, not just the decision). For markdown, wikilinks + a derived index (Basic Memory, §5) capture much of this at near-zero infrastructure cost.

## 4. Not running out of computer

**Checkpoint/resume — LangGraph checkpointers** (primary docs: https://docs.langchain.com/oss/javascript/langgraph/checkpointers). A checkpoint is a state snapshot at every **super-step**, and **pending writes are persisted inside a step**, so on resume the successful nodes of an interrupted step are not re-run. This buys fault tolerance, time-travel/forking, and human-in-the-loop interrupt/resume. Backends scale with need: InMemory (lost on restart), SQLite (local), Postgres (production); durability modes trade speed against consistency. LangGraph 1.0 GA'd 22 Oct 2025. The pattern transfers without the framework: persist state after every expensive step, in a form a fresh process can resume from.

**Anthropic, "Effective harnesses for long-running agents" (26 Nov 2025)** — https://www.anthropic.com/research/effective-harnesses-for-long-running-agents. Compaction alone is insufficient for multi-session work. Their pattern: an **initializer agent** (first session only) creates `init.sh`, a progress file (`claude-progress.txt`), a git repo, and a structured **`feature_list.json`** (200+ features, all initially failing; the coding agent may only flip the `passes` field). Each later **fresh-context session**: read the progress file + `git log --oneline -20` + feature list, smoke-test, implement **one** feature, end with a commit + progress update. This directly fixes one-shotting/context exhaustion, premature victory declarations, and undocumented buggy handoffs — the exact failure modes of scheduled background jobs here.

**Prompt caching economics.** Manus (§2): cache hit rate is the top production metric; ~10× cost difference between cached and uncached input. Rules that recur across Anthropic/Manus/Mastra: stable prefix first, **no volatile timestamps in the prefix**, append-only history, don't edit mid-history, don't add/remove tools mid-run; Mastra OM's stable observation prefix yields a further 4–10× cost cut (secondary sourcing).

**Small-model routing and delegation.** Every serious memory system uses a small model for the high-volume, low-judgement work (Mem0 extraction on gpt-4o-mini-class models; Mastra observation on gpt-5-mini; QMD's local sub-2B models) and reserves the frontier model for answering. A hardened "Ralph Loop" case study (https://seevali.dev/builds/hardening-the-ralph-loop/) adds the operational details: fresh bounded agents per story, role-based model tiers (cheap model for state management, mid for development, strongest for review — a weak reviewer costs more downstream than it saves), prompt caching, turn caps, spend caps, and an independent build/test gate before commit. Its warning is equally valuable: a fresh-context loop still paid **68,453 cache-creation tokens for a one-turn "hi"** on the cheapest model — fixed harness overhead dominates small tasks, so batch small work instead of spawning per-item agents.

**Batch + shard checkpointing.** Offline batch inference runs 5–10× cheaper per token than idle online serving (70–90% vs 20–40% utilisation; Spheron guide, Apr 2026: https://www.spheron.network/blog/batch-llm-inference-gpu-cloud/). The transferable pattern needs no GPU: split a corpus into shards (10–50K docs there; scale down freely), have the worker **mark a shard complete only after its output is fully written and synced**, and on restart skip completed shards. This is the correct shape for any multi-hour file-processing job on this VM.

**OS-level bounds.** Practitioner guidance (https://os.moda/blog/run-ai-agent-24-7): run each agent/job under **systemd with `MemoryMax=`, `CPUQuota=`, a Restart policy, and journald `SystemMaxUse=`**; a per-job cgroup scope (e.g. `systemd-run --user --scope -p MemoryMax=4G …`) bounds the daemon *and its children* in aggregate, so one job's leak becomes that job's restart, not the VM's OOM-kill of both agents. The same source notes agent memory grows monotonically (context + embeddings + tool results) until OOM unless actively trimmed — bounds plus checkpointing (§above) are complements, not alternatives.

**Streaming / not loading wholes.** The strongest *sourced* support is Anthropic's just-in-time pattern (§2: `head`/`tail`, targeted queries, paths as identifiers) plus JetBrains' finding that ~84% of trajectory tokens are observations that can be masked and re-fetched. **Gap:** no dedicated benchmark or paper was found that benchmarks streaming/chunked file processing for agents specifically — treat chunked reading, line-streaming and bounded buffers as standard engineering practice consistent with those sources, not as a benchmarked claim.

## 6. Multi-agent shared memory

**The blackboard pattern** (origin: Hearsay-II) — Agents don't message each other directly; they read/write a **shared store**, and a control/scheduler component decides who acts next. Modern evidence: Google's blackboard multi-agent system (Salemi et al., arXiv:2510.01285, 2025) — a central agent posts requests to the blackboard and subordinates volunteer by capability — reports **+13–57% relative task success** vs alternatives; LbMAS (arXiv:2507.01701) shows a blackboard design using **fewer tokens** at competitive quality. Via https://github.com/joona-t/blitz-swarm/blob/HEAD/Memory%20architecture%20for%20a%20parallel%20AI%20agent%20swarm.md.

**What "shared" must mean — governed memory.** A useful requirements analysis (https://caura.ai/blog/multi-agent-systems-explained/): a shared decision must be **persistent** (outlives the turn), **queryable** (findable by an agent that doesn't know it exists), and **enforceable/scoped** (binding, with access scope). A plain shared vector store fails the third: stale and out-of-scope facts return together with no resolution mechanism. Orchestrator-worker setups fail the first two for parallel workers, who cannot see each other — Anthropic's own multi-agent research system duplicated work exactly this way (one subagent researching the 2021 chip crisis while two duplicated the 2025 supply chain). The same system's fix is instructive: the lead agent **saves its plan to external memory** because >200K-token contexts truncate.

**G-Memory** (NeurIPS 2025 Spotlight, arXiv:2506.07398; https://github.com/bingreeky/GMemory; listing: https://neurips.cc/virtual/2025/loc/san-diego/poster/116187) — A three-tier graph for agent teams: **Insight** graph (abstracted lessons) / **Query** graph (tasks) / **Interaction** graph (raw collaboration trajectories). Bidirectional traversal retrieves relevant insights plus condensed trajectories, customised per agent, and the hierarchy evolves with each trial. **+20.89 embodied-task success, +10.12 knowledge-QA** across 5 benchmarks, 3 backbones and 3 frameworks (ChatDev/MetaGPT/AutoGen) with no framework modification. This is the strongest published design specifically for *persistent collaborating agents building shared context over time*.

**Shipping implementations of shared + private memory:**
- **agentmemory** (§5): one server, `AGENT_ID` + private/shared namespaces — two agents get both a shared store and scratch space, today, in one process.
- **Honcho** (§1): pointing two integrations at the same workspace yields one shared memory with per-peer models — each agent also builds a model of the *other* agent.
- **Letta**: shared memory blocks and the git-backed MemFS let multiple agents share memory with git history as the conflict record.
- **LangGraph**: a shared typed state graph + checkpointer enforces single-writer state discipline (§4).
- **MIRIX** (§1): manager-agent-per-store design is explicitly multi-agent.

**Practical stack** (from the swarm research note above): Redis blackboard (hashes + pub/sub) + SQLite in WAL mode as the persistent layer + a semantic index (LanceDB); note that storage latency (0.1ms Redis vs 5ms Postgres) is noise next to 500–5,000ms LLM calls — choose for operability, not speed. For two agents on one VM, the lightweight equivalent is: **one shared directory/store, append-only decision log, per-agent private namespaces, and a rule that both agents read the shared log before acting.** Append-only/CRDT-style writes avoid merge conflicts; git (as in MemFS) gives the same property for files.

## 7. Evaluation and silent degradation

### How to measure

- **Separate the layers.** Report **retrieval** (Recall@k — distinguishing *any-hit* from *strict recall-all*, MRR) separately from **end-to-end QA** (LLM-as-judge score, F1, exact match — always naming the answer model *and* judge model), plus **cost, p50/p95 latency, tokens per query, and context tokens used**. A system can win QA by stuffing context while its retrieval is poor, and vice versa.
- **Benchmarks:** LoCoMo and LongMemEval (§1) for conversational recall; BEAM for 1M–10M scale; LongMemEval-V2 for agent trajectories; MemoryArena for memory-guided action; MemoryAgentBench for conflict resolution/forgetting; **HaluMem** (~15K memory points, 3.5K questions) for locating *where* false information enters — extraction hallucination vs omission vs update error; DMR is the older MemGPT-era benchmark.
- **A free starting harness:** LongMemEval ships a **retrieval-only track** (`print_retrieval_metrics.py`, numpy only, no API key) — runnable on this VM today (https://github.com/xiaowu0162/LongMemEval).
- **Longitudinal/personal eval:** ~30 canary questions drawn from the agents' *own* history, re-asked monthly, plus a memory-on/memory-off ablation and per-category breakdowns. This catches the degradation modes below, which one-shot benchmarks structurally miss.

### How memory silently degrades

**Task success hides memory failure.** "Beyond Task Completion" (arXiv:2512.12791, Dec 2025, via secondary summaries): agents completed tasks while memory retrieval recall was only **13.1%** in complex scenarios (0.67 failures/session in simple settings → 3.67 in complex ones). Measure retrieval directly; never infer memory health from task completion.

**Poisoning.** MINJA and MemoryGraft (2025) demonstrate **query-only memory poisoning — no elevated privileges needed — with 95% injection rate / 70% attack success** (via https://github.com/gatsby23/ai-system-design-guide/blob/HEAD/07-agentic-systems/05-agent-memory-and-state.md); planted memories can fire weeks later (Unit 42 reporting). A Jul 2026 preprint (MemGhost, single-preprint claim — treat cautiously) claims one crafted email can plant a persistent false memory (87.5% vs an OpenClaw/GPT-5.4 setup). Mitigations: **write-gating and provenance** — never let untrusted content (email bodies, web pages, tool output) write to long-term or procedural tiers without verification; consistency-check before consolidation (SSGM below).

**Drift and the compounding loop.** The SSGM framework (arXiv:2603.11768, https://arxiv.org/html/2603.11768v1) models three coupled stages — **poisoning at ingestion, semantic drift at consolidation, hallucination at retrieval** — that compound over time; iterative summarisation is the drift engine (§2, ACE context collapse). "Agent Drift" (arXiv:2601.04170, Jan 2026) documents semantic drift over long interactions and proposes episodic consolidation as mitigation. **Procedural drift is the highest-stakes variant**: one bad playbook/skill entry propagates to every future invocation.

**Stale facts and contradictions.** The proven mitigation is Graphiti's bitemporal pattern (§1): `valid_from`/`valid_to`/`invalid_at`, **invalidate rather than delete**, belief status ACTIVE / SUPERSEDED / RETRACTED (belief revision, not last-write-wins), TTLs on session-level preferences, decay-weighted retrieval, and asking the user on outright contradiction. Note MemoryAgentBench's ≤28% ceiling (§1): no current system does this well automatically — a manual frontmatter convention (`valid_from`, `superseded_by`) in markdown captures most of the value.

**The Day-30 problem.** Unpruned episodic stores fill with noise and quality drops noticeably around ~30 days in (practitioner reports). Mitigations: a **scheduled consolidation job** that merges duplicates and prunes low-utility entries, quality/heat-weighted retrieval (§1, MemoryOS/FadeMem), ground-truth anchoring to raw episodes, and the canary eval above to detect the drop when it happens.

## Shortlist — most promising, practical, free approaches for this two-agent, file-based setup

Ranked by expected impact for two agents on one small VM with existing markdown memory. All are free; most require no new database.

| # | Approach | One-line reason |
|---|---|---|
| 1 | **Observation masking / tool-result clearing + a structured state file (todo/progress) recited at the end of context** | Cheapest fix with the strongest evidence: JetBrains showed masking matches/beats summarisation at −52% cost, and Manus/Anthropic show recitation defeats lost-in-the-middle and goal drift. |
| 2 | **Anthropic's long-running harness pattern: progress file + feature list + git commit per step for every long job** | Directly fixes premature "done", undocumented handoffs and context exhaustion across sessions — the scheduled-job failure modes here (§4). |
| 3 | **Hybrid search over the *existing* markdown (SQLite FTS5/BM25 + sqlite-vec + RRF + small local reranker — QMD, or the agentmemory/Basic Memory pattern) wired to a session-start search-before-answer rule** | Fixes "retrieval depends on remembering to search"; hybrid+rerank is the measured retrieval winner and BM25 alone already hits 96.2% any-hit@5 (§3). |
| 4 | **Progressive disclosure retrieval (index → timeline → full record)** | ~10× fewer tokens per recall, which simultaneously cuts cost and context rot (§2, §3). |
| 5 | **Sleep-time/background consolidation with a small cheap model: dated observation log, delta edits only (ACE), always summarising from raw files, never from summaries** | Gets consolidation's benefits while structurally preventing summary drift and context collapse (§1, §2, §7). |
| 6 | **Checkpoint/resume + shard-complete markers for background jobs, each under systemd `MemoryMax`/`CPUQuota`** | A killed job resumes instead of restarting, and one job's leak can no longer OOM the whole VM or the other agent (§4). |
| 7 | **Stable-prefix prompt-caching discipline + small-model routing (extraction/summarisation/review triage on the cheap model)** | ~10× on cached input and small models for high-volume low-judgement work is where the real money is (§2, §4). |
| 8 | **Temporal validity in frontmatter (`valid_from`, `superseded_by`; invalidate, never delete)** | Captures Graphiti's core win — correct handling of changed preferences, prices and positions — with zero new infrastructure (§1, §7). |
| 9 | **Decay-ranked forgetting (heat/Ebbinghaus score in the index) + a scheduled dedupe/prune job** | Prevents the Day-30 noise collapse without ever hard-deleting ground truth (§1, §7). |
| 10 | **Shared-blackboard discipline for the two agents: one shared store, private + shared namespaces, append-only decision log both must read before acting** | The lightweight, proven core of G-Memory/blackboard research; stops duplicated work and lost track of each other (§6). |
| 11 | **Trial one drop-in store — Hindsight (self-hosted) or MemPalace (verbatim) — only after items 1–10** | Both are free and strong, but the harness fixes above are prerequisites, and their headline benchmarks are vendor/contested (§1, §3). |
| 12 | **A tiny personal eval harness: LongMemEval retrieval-only track + ~30 canary questions from the agents' own history, run monthly** | The only way to *see* silent degradation (poisoning, drift, staleness) before it bites; the retrieval track is free and needs no API key (§7). |

## Could not verify / open questions

- **Benchmark incomparability is unresolved field-wide.** Mem0's new headline scores are hosted-platform-only; Hindsight's top scores are vendor/leaderboard with claimed (not inspected) independent reproduction; MemPalace's R@5 is contested by an audit; EverOS's 93.05% LoCoMo lacks published methodology; LoCoMo's own answer key is ~6.4% wrong. No independently-run, same-harness comparison of Letta/Mem0/Graphiti/Hindsight exists as of this research.
- **LangMem latency** (a 59.82s p95 search figure) comes from a single secondary survey and was not verified; treat LangMem as offline/background-grade only if it proves true.
- **OpenViking/TencentDB/EverOS/MemOS star counts and TencentDB's license** partly rest on secondary surveys dated Sept–Nov 2026; OpenViking (41,705, AGPL-3.0) and EverOS (13,842, Apache-2.0) were re-verified from their repos on 2026-11-07, but TencentDB's license remains genuinely ambiguous — read it before any adoption.
- **No dedicated benchmark exists** (that this research found) for streaming/bounded-memory file processing by agents; §4's streaming guidance is engineering practice aligned with Anthropic/JetBrains sources, not a measured result.
- **Mission parameters not specified:** the VM's actual RAM/CPU, which LLM providers/models the two agents use, and implementation languages were not stated. The shortlist assumes API-based LLMs, a small (2–8GB-class) Linux VM, and existing markdown files; a fully local-model setup would re-rank QMD-style local models higher and LLMLingua-class compression lower.
- All sources were read through the search index / text fetch on 2026-11-07 (flag: *index*); no interactive live-browser verification (e.g. running a repo, checking a live leaderboard) was performed.
